  Interfaces:
    Browser        → Dashboard Server : HTTP GET  /        (dashboard HTML)
    Browser        → Dashboard Server : HTTP GET  /camera  (MJPEG proxy)
    Browser        → Dashboard Server : HTTP GET  /camera/ping  (health poll)
    Browser        → Dashboard Server : HTTP GET  /state   (JSON telemetry)
    Browser        → Dashboard Server : HTTP GET  /config  (JSON config)
    Browser        → Dashboard Server : HTTP POST /drive   (JSON steer+speed)
    Browser        → Dashboard Server : HTTP POST /estop
    Dashboard Svr  → Camera Server    : HTTP GET  /stream  (MJPEG proxy src)
    Dashboard Svr  → Camera Server    : HTTP GET  /health  (200/503)
    Dashboard Svr  → black_mata_fw    : USB Serial binary frames, 115200 baud
                                        Jetson→OpenCM fixed-length packet:
                                          header | seq | timestamp_ms |
                                          8× (mode, target, enable_torque) |
                                          payload | CRC
    black_mata_fw  → Dashboard Svr    : USB Serial binary frames, 115200 baud
                                        OpenCM→Jetson fixed-length packet:
                                          header | seq | timestamp_ms |
                                          e-stop_state | IMU (reserved) |
                                          8× (available, mode, pos, speed,
                                          temp, voltage) | payload | CRC
    black_mata_fw  → AX-12A           : Dynamixel Protocol 1.0, 1 Mbaud

  6. SEQUENCE DIAGRAM — CAMERA STREAM FLOW  (~30 fps)

  Browser         Dashboard Server    Camera Server       Camera (camera.py)   USB Camera
  ─────────       ────────────────    ─────────────       ──────────────────   ──────────
     │                 │                   │                     │                  │
     │── GET /camera ─►│                   │                     │                  │
     │                 │── GET /stream ───►│                     │                  │
     │                 │                   │── get_frame() ─────►│                  │
     │                 │                   │◄── JPEG bytes ──────│                  │
     │◄── multipart ───│◄── multipart ─────│                     │                  │
     │    frame        │    chunk          │── get_frame() ─────►│                  │
     │                 │                   │◄── JPEG bytes ──────│                  │
     │◄── next frame ──│◄── next chunk ────│                     │                  │
     │    (continuous) │    (continuous)   │   ... repeats ...   │                  │


  Browser polls /camera/ping every 2 s via XHR:
    → Dashboard Server checks Camera Server GET /health
    → 200 if is_healthy(), 503 if reconnecting
    → On 503: browser blanks stream, creates fresh <img> element on 200

================================================================================
  9. ARCHITECTURE DECISION RECORDS
================================================================================

  ──────────────────────────────────────────────────────────────────────────
  ADR-001  Use HTTP POST for drive command channel
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted  (supersedes original WebSocket decision)
  Date    : 2026-05-25

  Context
    Drive commands need to reach the robot at ~10 Hz from WASD keyboard
    input. The original design used WebSocket for low-overhead persistent
    connection. However the Robot Agent (FastAPI/main.py) was removed in
    favour of the simpler stdlib HTTP dashboard server.

  Decision
    Use HTTP POST to /drive. The dashboard JS sends a POST every 100 ms
    while a key is held. A keepalive loop on the server sends e-stop frames
    if no POST is received within 300 ms.

  Consequences
    + No WebSocket infrastructure needed — stdlib HTTP handles everything.
    + Simpler to debug (standard HTTP tools work).
    + Adequate for 10 Hz keyboard drive on a LAN.
    - Higher per-message overhead than WebSocket (HTTP headers each POST).
    - Not suitable for high-frequency gamepad input at 50 Hz (revisit for v2).

  ──────────────────────────────────────────────────────────────────────────
  ADR-002  Use MJPEG over HTTP for camera streaming
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-11

  Context
    The operator needs a live camera feed rendered in the browser.
    Options evaluated: WebRTC, HLS, WebSocket binary, MJPEG over HTTP.

  Decision
    Serve MJPEG as a multipart HTTP stream. Consume in browser via <img>.

  Consequences
    + Zero browser-side code (native <img> support).
    + No signalling server or STUN/TURN infrastructure.
    + OpenCV imencode() produces JPEG frames natively.
    - One-way stream only; no audio.
    - Higher bandwidth than H.264. Acceptable for LAN/tunnel.
    - Latency ~100–300 ms. Sufficient for teleoperation at v1.

  ──────────────────────────────────────────────────────────────────────────
  ADR-003  Use ngrok for public demo access
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted  (supersedes original Tailscale decision)
  Date    : 2026-05-25

  Context
    The robot needs to be reachable by people outside the local network
    for demos. The original plan was Tailscale (persistent VPN mesh),
    which requires a Tailscale account on every viewer's machine.
    The actual requirement is: share a URL for a demo session, not
    maintain a permanent private network.

  Decision
    Use ngrok free tier. Run `ngrok http 8082` at demo time. Share the
    temporary HTTPS URL. Stop when done. URL changes each session
    intentionally — the robot is only accessible during active demos.

  Consequences
    + No installation required on the viewer's side.
    + Zero ongoing cost (free tier sufficient).
    + URL expiry is a safety feature — no persistent public exposure.
    - URL changes each session (not a stable address).
    - Requires ngrok account and one-time auth token setup on Jetson.
    - Free tier rate-limits connections.

  ──────────────────────────────────────────────────────────────────────────
  ADR-004  Use black_mata_firmware over host-side DynamixelSDK
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-11

  Context
    Dynamixel servos can be controlled from the Jetson directly using
    DynamixelSDK (Python), or via a microcontroller running Dynamixel2Arduino.

  Decision
    All Dynamixel complexity lives in the black_mata_firmware on OpenCM9.04.
    The Jetson sends binary frames over USB Serial. No DynamixelSDK on host.

  Consequences
    + Host code decoupled from Dynamixel protocol details.
    + OpenCM9.04 handles half-duplex TTL bus timing natively.
    - Firmware update required to add new servo operations.
    - Extra USB-Serial hop adds ~1–2 ms latency per command.

  ──────────────────────────────────────────────────────────────────────────
  ADR-005  Use stdlib HTTP server for Dashboard and Camera
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted  (supersedes original FastAPI decision)
  Date    : 2026-05-25

  Context
    The original design used FastAPI + uvicorn (main.py) as a single
    Robot Agent process. This added FastAPI and uvicorn as dependencies
    and required async programming. The API became stale as the robot
    evolved (renamed kwargs, wrong device paths). The dashboard server
    (tools/dashboard/server.py) grew to cover the same responsibilities
    using only Python stdlib HTTP.

  Decision
    Remove main.py. Use Python stdlib BaseHTTPRequestHandler for both
    the Dashboard Server and Camera Server. No external HTTP framework.

  Consequences
    + No extra dependencies (stdlib only).
    + Easy to read and modify — no async/await complexity.
    + Dashboard and camera are separate processes — can restart independently.
    - No async I/O — blocking handlers use ThreadingHTTPServer.
    - Less suitable if concurrency requirements grow (revisit for v2).

  ──────────────────────────────────────────────────────────────────────────
  ADR-006  Use Vanilla JS for the Operator Dashboard
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-11

  Context
    The dashboard needs live video, keyboard input, e-stop, and a status
    panel. Options: React, Vue, Svelte, Vanilla JS.

  Decision
    Single HTML file, built-in browser APIs only. No build step.

  Consequences
    + No npm, no bundler, no framework to learn.
    + Served as a static string from the Python server.
    - Not suitable if dashboard grows beyond ~500 LOC (revisit for v2).

  ──────────────────────────────────────────────────────────────────────────
  ADR-007  Use binary fixed-length frames for Jetson ↔ OpenCM serial link
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-16

  Context
    Text-based serial protocol sends one command per servo per tick.
    At 10 Hz with 8 servos this produces excessive serial round-trips.
    data_structure.txt described a binary packet design bundling all
    8 servo targets in one frame.

  Decision
    Fixed-length binary frame pair with CRC-16:
      Jetson → OpenCM : header | seq | timestamp_ms | 8× servo targets | CRC
      OpenCM → Jetson : header | seq | timestamp_ms | e-stop | 8× servo state | CRC

  Consequences
    + All servo targets dispatched atomically in one write.
    + State cache makes /state instant (no serial blocking).
    + CRC catches bit errors.
    - Binary protocol requires tooling to debug.

  ──────────────────────────────────────────────────────────────────────────
  ADR-008  Dual-layer e-stop
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-16

  Context
    If the operator's connection drops, the robot holds its last commanded
    state indefinitely. Two independent watchdog layers are needed.

  Decision
    Layer 1 — Dashboard Server keepalive loop (Python):
      If no /drive POST received in >300 ms, sends zero-speed binary frame.

    Layer 2 — black_mata_firmware watchdog (C++):
      If no valid frame received in >500 ms, zeros all drive speeds and
      steering independently of the Jetson.

    OpenCM is powered from the 12V rail directly (master switch on board),
    independent of Jetson power. Layer 2 fires even on a Jetson crash.

  Consequences
    + Robot stops safely on network fault, browser crash, or Jetson crash.
    - 500 ms threshold must be tuned per deployment.

  ──────────────────────────────────────────────────────────────────────────
  ADR-009  Separate camera into its own process
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-25

  Context
    The original design had one Robot Agent process owning both serial and
    camera. Camera failures (device lost, reconnecting) could block or crash
    the drive path. Separating them isolates the failure domain.

  Decision
    Camera Server (camera_test.py) runs as a separate process on port 8083.
    Dashboard Server proxies the stream and health-checks via /health endpoint.
    Either process can be restarted independently without affecting the other.

  Consequences
    + Camera restart does not interrupt drive control.
    + Dashboard auto-reconnects stream when camera server recovers.
    + Camera hardware reconnect handled internally (no process restart needed).
    - Two processes to manage instead of one.
    - Extra HTTP hop for camera stream (localhost proxy).

  ──────────────────────────────────────────────────────────────────────────
  ADR-010  Use udev symlink for stable camera device path
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-25

  Context
    The USB camera enumerates as /dev/video0 or /dev/video1 depending on
    boot order and USB reconnect sequence. Scripts hardcoding a device index
    break on reconnect.

  Decision
    Install a udev rule (tools/camera/setup_udev.py) that creates a stable
    symlink /dev/robot_camera tied to the camera's USB vendor/product ID.
    All scripts use /dev/robot_camera as the default device path.

  Consequences
    + Device path is stable across reboots and reconnects.
    + Works for any robot unit with the same camera model.
    - One-time setup step required per robot (run setup_udev.py once).

  ──────────────────────────────────────────────────────────────────────────
  ADR-011  Camera auto-reconnect with health signalling
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-25

  Context
    USB cameras can physically disconnect mid-session (cable pull, power
    glitch). The operator needs the dashboard to go blank on disconnect
    and recover automatically when the camera is reconnected — without
    restarting any process or refreshing the browser.

  Decision
    Three-layer recovery:
      1. camera.py _reconnect(): on 10 consecutive failed reads, releases
         VideoCapture, clears frame cache, polls /dev/robot_camera every 2 s.
      2. camera_test.py /health: returns 503 while _reconnecting=True,
         200 otherwise. Camera Server process stays alive during reconnect.
      3. Dashboard JS: polls /camera/ping (→ /health) every 2 s. On 503:
         blanks stream. On 200: replaces <img> element with fresh one
         (forces new browser request) and restores stream display.

  Consequences
    + Full hardware disconnect/reconnect handled without human intervention.
    + Dashboard correctly reflects camera availability state.
    + Browser cache issues avoided by replacing the DOM element on reconnect.
    - 2 s polling interval means up to 2 s lag before dashboard reacts.

  ──────────────────────────────────────────────────────────────────────────
  ADR-012  Use Linux evdev + ESP32-C6 HCI adapter for gamepad input
  ──────────────────────────────────────────────────────────────────────────
  Status  : Accepted
  Date    : 2026-05-26

  Context
    The robot needs gamepad (Machenike G3 V2) input for manual drive control.
    Two architectural approaches were considered:

    Option A — Browser Gamepad API (original plan):
      Browser reads gamepad via navigator.getGamepads(), sends drive POSTs
      to Dashboard Server. No Jetson-side code needed.

    Option B — Linux evdev on Jetson (adopted):
      Gamepad pairs to Jetson over Bluetooth. Jetson reads input via
      python-evdev. A future gamepad_drive.py process sends frames directly
      to serial_driver.py, bypassing the browser entirely.

    The Jetson has no built-in Bluetooth. A USB BT dongle (broken) was the
    original plan. Replaced temporarily with an ESP32-C6 acting as a BLE
    HCI UART adapter (hciattach registers it as hci0).

  Decision
    Use Linux evdev on the Jetson. ESP32-C6 provides BLE connectivity until
    a USB BT dongle is sourced. Gamepad input is decoupled from the browser —
    the robot can be driven with no browser session open.

  Consequences
    + Gamepad input path is independent of browser and network.
    + Identical /dev/input/eventX interface regardless of BT hardware
      (dongle, ESP32, or future permanent adapter — nothing else changes).
    + Lower latency than browser POST loop for high-frequency gamepad input.
    + Axis calibration (hardware + software) fully corrects asymmetric ranges.
    - Requires Bluetooth stack on Jetson (bluetoothd, hciattach).
    - ESP32-C6 is BLE-only; controller must support BLE (G3 V2 does).
    - ESP-IDF v5 required to build HCI firmware (not arduino-cli compatible).
    - Browser Gamepad API path is still planned: operator plugs a gamepad
      into their own machine and controls the robot remotely over any
      network without needing BT on the Jetson. Deferred to next sprint.
