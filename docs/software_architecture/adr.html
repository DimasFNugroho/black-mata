ADR-001 Use HTTP POST for the drive command channel
Accepted supersedes WebSocket 2026-05-25
▶
Context

Drive commands need to reach the robot at ~10 Hz from WASD keyboard input. The original design used WebSocket for a low-overhead persistent connection. However the FastAPI Robot Agent (main.py) was removed in favour of the simpler stdlib HTTP dashboard server (see ADR-005).

Decision

Use HTTP POST to /drive. The dashboard JS sends a POST every 100 ms while a deadman is held. A keepalive loop on the server sends an e-stop frame if no POST is received within 300 ms.

Consequences
  • No WebSocket infrastructure needed — stdlib HTTP handles everything.
  • Simpler to debug (standard HTTP tools work).
  • Adequate for 10 Hz keyboard drive on a LAN.
  • Higher per-message overhead than WebSocket (HTTP headers each POST).
  • Not suitable for high-frequency gamepad input at 50 Hz (revisit for v2).
ADR-002 Use MJPEG over HTTP for camera streaming
Accepted 2026-05-11
▶
Context

The operator needs a live camera feed rendered in the browser. Options evaluated: WebRTC, HLS, WebSocket binary frames, and MJPEG over HTTP.

Decision

Serve MJPEG as a multipart/x-mixed-replace HTTP stream. The dashboard consumes it with a plain <img src="/camera"> tag — no JavaScript involved.

Consequences
  • Zero browser-side code — the <img> tag handles the stream natively.
  • No signalling server or STUN/TURN infrastructure (unlike WebRTC).
  • OpenCV imencode() produces JPEG frames natively.
  • One-way stream only; no audio.
  • Higher bandwidth than H.264. Acceptable over LAN and tunnel for v1.
  • Latency ~100–300 ms. Sufficient for teleoperation at v1.
ADR-003 Use ngrok for public demo access
Accepted supersedes Tailscale 2026-05-25
▶
Context

The robot needs to be reachable by people outside the local network for demos. The original plan was Tailscale (persistent VPN mesh), which requires a Tailscale account on every viewer's machine. The actual requirement is to share a URL for a demo session, not maintain a permanent private network.

Decision

Use the ngrok free tier. Run ngrok http 8082 at demo time, share the temporary HTTPS URL, and stop when done. The URL changes each session intentionally — the robot is only accessible during active demos.

Consequences
  • No installation required on the viewer's side.
  • Zero ongoing cost (free tier sufficient).
  • URL expiry is a safety feature — no persistent public exposure.
  • URL changes each session (not a stable address).
  • Requires an ngrok account and a one-time auth-token setup on the Jetson.
  • Free tier rate-limits connections.
ADR-004 Use black_mata_firmware over host-side DynamixelSDK
Accepted 2026-05-11
▶
Context

Dynamixel servos can be controlled from the Jetson directly using the Python DynamixelSDK, or via a microcontroller running Dynamixel2Arduino. The OpenCM9.04 is already present in the robot.

Decision

All Dynamixel complexity lives in the black_mata_firmware on the OpenCM9.04. The Jetson sends binary frames over USB Serial. No DynamixelSDK on the host.

Consequences
  • Host code is decoupled from Dynamixel protocol details and baud timing.
  • The OpenCM9.04 handles half-duplex TTL bus direction switching natively.
  • A firmware update is required to add new servo operations.
  • Extra USB-Serial hop adds ~1–2 ms latency per command batch.
ADR-005 Use the Python stdlib HTTP server for Dashboard and Camera
Accepted supersedes FastAPI 2026-05-25
▶
Context

The original design used FastAPI + uvicorn (main.py) as a single Robot Agent process. This added FastAPI and uvicorn as dependencies and required async programming. The API became stale as the robot evolved (renamed kwargs, wrong device paths). The dashboard server (tools/dashboard/server.py) grew to cover the same responsibilities using only the Python stdlib HTTP server.

Decision

Remove main.py. Use the stdlib BaseHTTPRequestHandler for both the Dashboard Server and the Camera Server. No external HTTP framework.

Consequences
  • No extra dependencies (stdlib only).
  • Easy to read and modify — no async/await complexity.
  • Dashboard and camera are separate processes — can restart independently.
  • No async I/O — blocking handlers use ThreadingHTTPServer.
  • Less suitable if concurrency requirements grow (revisit for v2).
ADR-006 Use Vanilla JS for the Operator Dashboard
Accepted 2026-05-11
▶
Context

The dashboard needs live video, keyboard input, e-stop, and a status panel. Options: React, Vue, Svelte, Vanilla JS.

Decision

A single set of static files using built-in browser APIs only (Fetch for telemetry/drive, <img> for the stream, EventSource/SSE for the pairing modal). No build step.

Consequences
  • No npm, no bundler, no framework to learn.
  • Served as static files from the Python server.
  • Not suitable if the dashboard grows substantially in v2 (maps, waypoint editor, tuning panels). Revisit with a lightweight framework at that point.
ADR-007 Use binary fixed-length frames for the Jetson ↔ OpenCM serial link
Accepted 2026-05-16
▶
Context

A text-based serial protocol sends one command per servo per tick. At 10 Hz with 8 servos this produces excessive serial round-trips. data_structure.txt described a binary packet design bundling all 8 servo targets into one frame.

Decision

A fixed-length binary frame pair with CRC-16:

Jetson → OpenCM: header | seq | timestamp_ms | 8× servo targets | CRC
OpenCM → Jetson: header | seq | timestamp_ms | e-stop | 8× servo state | CRC

Consequences
  • All servo targets are dispatched atomically in one write.
  • A state cache makes /state instant (no serial blocking).
  • CRC catches bit errors.
  • A binary protocol requires tooling to debug.
ADR-008 Dual-layer e-stop
Accepted 2026-05-16
▶
Context

If the operator's connection drops, the robot holds its last commanded state indefinitely. Two independent watchdog layers are needed.

Decision

Layer 1 — Dashboard Server keepalive loop (Python): if no /drive POST is received in >300 ms, send a zero-speed binary frame.

Layer 2 — black_mata_firmware watchdog (C++): if no valid frame is received in >500 ms, zero all drive speeds and steering independently of the Jetson. The OpenCM is powered from the 12V rail directly (master switch on board), independent of Jetson power, so Layer 2 fires even on a Jetson crash.

Consequences
  • Robot stops safely on network fault, browser crash, or Jetson crash.
  • The 500 ms threshold must be tuned per deployment.
ADR-009 Separate the camera into its own process
Accepted 2026-05-25
▶
Context

The original design had one Robot Agent process owning both serial and camera. Camera failures (device lost, reconnecting) could block or crash the drive path. Separating them isolates the failure domain.

Decision

The Camera Server (camera_test.py) runs as a separate process on port 8083. The Dashboard Server proxies the stream and health-checks via the /health endpoint. Either process can be restarted independently.

Consequences
  • A camera restart does not interrupt drive control.
  • The dashboard auto-reconnects the stream when the camera server recovers.
  • Camera hardware reconnect is handled internally (no process restart needed).
  • Two processes to manage instead of one.
  • Extra HTTP hop for the camera stream (localhost proxy).
ADR-010 Use a udev symlink for a stable camera device path
Accepted 2026-05-25
▶
Context

The USB camera enumerates as /dev/video0 or /dev/video1 depending on boot order and USB reconnect sequence. Scripts hardcoding a device index break on reconnect.

Decision

Install a udev rule (tools/camera/setup_udev.py) that creates a stable symlink /dev/robot_camera tied to the camera's USB vendor/product ID. All scripts default to /dev/robot_camera.

Consequences
  • The device path is stable across reboots and reconnects.
  • Works for any robot unit with the same camera model.
  • A one-time setup step is required per robot (run setup_udev.py once).
ADR-011 Camera auto-reconnect with health signalling
Accepted 2026-05-25
▶
Context

USB cameras can physically disconnect mid-session (cable pull, power glitch). The operator needs the dashboard to go blank on disconnect and recover automatically when the camera is reconnected — without restarting any process or refreshing the browser.

Decision

Three-layer recovery:

  • camera.py _reconnect(): on 10 consecutive failed reads, releases VideoCapture, clears the frame cache, and polls /dev/robot_camera every 2 s.
  • camera_test.py /health: returns 503 while reconnecting, 200 otherwise. The Camera Server process stays alive during reconnect.
  • Dashboard JS: polls /camera/ping (→ /health) every 2 s. On 503 it blanks the stream; on 200 it replaces the <img> element with a fresh one and restores the stream.
Consequences
  • Full hardware disconnect/reconnect handled without human intervention.
  • The dashboard correctly reflects camera availability state.
  • Browser cache issues avoided by replacing the DOM element on reconnect.
  • The 2 s polling interval means up to 2 s lag before the dashboard reacts.
ADR-012 Use Linux evdev for gamepad input (RTL8761B USB BT dongle)
Accepted 2026-05-26 (rev. 05-31)
▶
Context

The robot needs gamepad (Machenike G3 V2) input for manual drive control. Two approaches were considered:

Option A — Browser Gamepad API (original plan): the browser reads the gamepad via navigator.getGamepads() and sends drive POSTs. No Jetson-side code.

Option B — Linux evdev on Jetson (adopted): the gamepad pairs to the Jetson over Bluetooth and the Jetson reads input via python-evdev. The reader lives as a GamepadReader thread inside the Dashboard Server (server.py), not a separate process.

The Jetson has no built-in Bluetooth, so a USB BT dongle is used. The chosen RTL8761B dongle ("BT 6.0", USB id 0bda:a760) does not work out of the box on L4T R32.7.x (kernel 4.9.337-tegra): NVIDIA's backported btrtl lacks the 8761B project-id entry and bails with "unknown project id 14".

Decision

Use Linux evdev on the Jetson, fed by an RTL8761B USB Bluetooth dongle. jetson_btrtl_8761b_fix.sh rebuilds btrtl.ko with the missing project-id entry, plants the 8761BU firmware, and blacklists the vendor rtk_btusb driver. Gamepad input is decoupled from the browser — the robot can be driven with no browser session open.

Consequences
  • Gamepad input path is independent of browser and network.
  • Identical /dev/input/eventX interface regardless of which BT adapter is used — only the kernel-level bring-up differs.
  • Lower latency than the browser POST loop for high-frequency gamepad input.
  • Axis calibration (hardware + software) fully corrects asymmetric ranges.
  • Requires a Bluetooth stack on the Jetson (bluetoothd, bluetoothctl).
  • The RTL8761B needs a patched btrtl.ko on the L4T 4.9 kernel; the fix must be re-applied if the module is replaced by an OS update.
  • The Browser Gamepad API path is still planned for remote operation over any network. Deferred to a next sprint.
ADR-013 Sudo-free in-browser pairing + one-time host commissioning
Accepted 2026-06-01
▶
Context

An end-user should be able to pair (and later swap) a Bluetooth gamepad from the dashboard alone — no terminal, no sudo. But pairing on BlueZ normally needs privileged setup (rfkill unblock, adapter power, ERTM, device bonds), and the Jetson's L4T 4.9 stack has quirks: bluetoothctl one-shots grab the TTY and hang; pairing/scanning across separate sessions drops the bond; the RTL8761B beacons sparsely at low RSSI. Doing all this safely at request time, as a non-root web process, is the constraint.

Decision

Split the work by lifetime into a three-tier model and push every privileged action out of the runtime path:

  • Tier 1 — Driver (once per OS image): jetson_btrtl_8761b_fix.sh.
  • Tier 2 — Commission (once per robot): setup_bluetooth_host.sh applies all root setup — ERTM disable, rfkill unblock, AutoEnable=true, dashboard user added to the bluetooth group, service enabled. After this the runtime needs no sudo.
  • Tier 3 — Verify (gate): check_bluetooth_host.sh, read-only PASS/WARN/FAIL, must pass on a cold boot.
  • Tier 4 — Acceptance: pair from the dashboard, no terminal/sudo.

commission_bluetooth.sh is a resumable, read-only guide across the reboots that separate the tiers; reset_bluetooth_host.sh reverts Tier 2 for re-testing. The pairing logic lives once in bt_setup.py, shared by the terminal wrapper (setup_gamepad.sh) and the dashboard, which drives the modal over Server-Sent Events (/api/gamepad/setup/*). Because the live-state widget and the pairing control are independent, a controller can be (re)paired even while one is connected. BlueZ-quirk mitigations baked into bt_setup.py: stdin=DEVNULL on every bluetoothctl call, a single session for remove→scan→pair→trust→connect, remove '*' before scanning, and a re-discovery wait until the target MAC re-advertises.

Consequences
  • End-user pairs/swaps controllers from the browser; no shell, no sudo.
  • All privilege is confined to a one-time, auditable commissioning step.
  • One pairing implementation for both terminal and browser.
  • Procedure is repeatable and verifiable on any black-mata (guide + gate + reset).
  • Commissioning requires one reboot between tiers, so it is a guided procedure rather than one script.
  • ERTM's modprobe.d option is not applied at boot on L4T 4.9; treated as informational since the G3 V2 pairs without it. If a future controller needs it, add a boot-time systemd one-shot.
ADR-014 Single-owner serial port — tuning vs. driving are mutually exclusive
Accepted 2026-06-01
▶
Context

Two browser tools talk to the OpenCM: the Operator Dashboard (tools/dashboard/server.py) for driving, and the Ackermann UI (tools/ackermann_ui/server.py) for parameter tuning, steer-centre calibration, and live servo state. Each opens the OpenCM serial port directly. A serial port has a single OS-level owner, so running both at once makes the second fail to open the port (or read corrupt data). Beyond the resource clash, the two are mutually exclusive activities: steer-centre calibration torques servos off so the wheels can be aligned by hand, which conflicts with the dashboard streaming drive frames.

Decision

Keep the two tools mutually exclusive — run one at a time. They share a handoff artifact: the Ackermann UI writes ackermann_config.json, and the dashboard re-reads it every 5 s at runtime. That file is the interface; there is intentionally no live process-to-process link.

Considered and rejected for now: a serial-broker daemon owning the port with both UIs as clients (the camera-server pattern, ADR-009) — correct long-term and the right move if simultaneous access is ever needed, but a real refactor and unnecessary while tuning and driving don't overlap; folding the Ackermann UI into the dashboard as a panel; and two live owners with locking (most work, bakes in the unsafe drive-while-calibrate case).

Consequences
  • Zero added infrastructure; the JSON handoff already exists.
  • The unsafe "drive while calibrating" case can't happen by construction.
  • The operator must stop one process before starting the other; no live tuning while driving.
  • If simultaneous access is ever required, revisit with the serial-broker option (ADR-009 is the precedent).
